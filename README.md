# 竞赛日报 · astrbot_plugin_contest_daily

[![AstrBot](https://img.shields.io/badge/AstrBot-%3E%3D4.16%2C%3C5-2f6fed)](https://github.com/AstrBotDevs/AstrBot)
![Python](https://img.shields.io/badge/python-3.9%2B-3776ab)
![License](https://img.shields.io/badge/license-MIT-green)

自动抓取 **Codeforces / 牛客** 赛程，定时推送到 QQ 群，并在**每场比赛开赛前 15 分钟**提醒；
群里还能随时查**任意用户的战绩卡片**（头像取不到就降级为名字首字母）；
日报末尾每天还会换一句**竞赛名言彩蛋**（`〖…〗`），名言库可在面板里**逐条查看 / 屏蔽 / 新增**；
战绩缓存用 **`/清缓存`** 一键清（CF、牛客分开）。

## 安装

**方式一：上传 zip**（推荐）
在 AstrBot WebUI → 插件市场 →「安装插件」→ 上传本仓库 Releases 里的 `astrbot_plugin_contest_daily.zip`。

**方式二：克隆到插件目录**
```bash
cd /path/to/astrbot/data/plugins
git clone https://github.com/BW-YuChen/astrbot_plugin_contest_daily.git
```
然后在 WebUI 里重载插件。

依赖只有标准库 + AstrBot 本体自带的 `aiohttp`，**无需浏览器、无需额外 pip 包**。

## 快速开始

1. 进群发 `@机器人 /订阅`，把当前群加进推送列表；
2. WebUI →「插件」→「竞赛日报」→ 配置里设好**推送时间**、**提前提醒分钟数**、**时区**；
3. 想立刻验证，用右侧「**推送测试**」标签页手动推一次。

常用指令、面板与配置项说明都在下方。

## 1.7.3 更新说明：修面板「订阅会话 3/2、-1 个待发」

实机截图：退订一个群后，顶部状态卡变成「订阅会话 **3 / 2**」「今天已推送 **-1 个待发**」。

**原因**：`sent_log.json` 是**只增不清**的幂等账本 —— 退订只从订阅表移除会话，
**故意不清它今天的推送记录**（这样当天「退订 → 重新订阅」不会把日报重收一遍）。
而状态卡之前直接 `count` 整个账本，那个已退订群的记录就被算了进去：
订阅 2 个、账本 3 条 → 3/2、待发 2−3 = **−1**。

**修法（双保险）**：

1. **后端口径修正**（`page_status`）：「今天已收到日报」只数**当前订阅表中**的会话
   （逐个 `daily_sent_on`），分子永远不会超过分母；
2. **前端钳位**：显示前 `min/max` 夹在 `[0, subs]`，就算账本被手工改出怪账也不会显示负数。

幂等语义没动：已退订群的记录继续躺在账本里，当天重新订阅也不会重收 —— 只是**不再被显示**。

## 1.7.2 更新说明：取消 QQ 头像，查不到就用名字首字母

> 需求原话：「干脆取消 QQ 头像的设置，查不到头像就降级为名字首字母，像前面某一版那样」

**删掉了整条 QQ 头像链路**（1.2.9 加进来的那套）：

| 删掉的东西 | 为什么 |
|---|---|
| `avatar_fallback_qq`、`qq_avatar_url_template`、`profile_avatar_source` 三个配置项 | 用户要求取消 QQ 头像设置；配置项少了也让插件页更干净（58 → **55** 项） |
| `_qq_avatar_urls()`（头像地址拼装）、`_avatar_source_mode()` | 只为 QQ 头像服务，随之删除 |
| `_QQ_PLACEHOLDER_MD5` + `_looks_like_qq_placeholder()`（默认灰图识别） | 认灰图的存在意义就是「QQ 头像可能回假图」，现在不会用 QQ 头像了，自然不需要 |
| `render_profile_card()` 的 `fallback_avatars` / `qq_first` 两个参数 | 渲染层只剩「平台头像」一拨，签名更干净 |

**保留的东西**：`_qq_appid()` 留着 —— 它现在只服务于「主动消息权限」启动预检（判断当前接的是不是
QQ 官方机器人适配器），与头像无关。`ephemeral_card_without_avatar`（没取到平台头像的卡不缓存、
发完即删）也保留，这正是 1.5.0 用户明确要过的行为。

**现在的行为**（两态，简单可预期）：

| 情况 | 卡片上 |
|---|---|
| CF 平台头像（大图或小图）拿到一个 | 真头像（并行取图，实测 ~1.2 秒） |
| 全部拿不到（图床 503 / 用户没上传过头像 / 超时 / 解码失败） | **名字首字母圆角块**，且这次档案不缓存、卡片图发完即删 |

> 为什么值得删：官方机器人的 openid 头像接口对**任何**参数都回 200 + 一张 40×40 默认灰图 ——
> 拿不到真头像，却要多养一条链路、两个配置项和一层灰图识别。
> 收益为零，删掉最干净。

## 1.7.1 更新说明：修「/清缓存 报必要参数缺失」

实机截图：`/清缓存` 和 `/清缓存 全部` 都报
「必要参数缺失。该指令完整参数： kind(str)=,extra(str)」。

**根因（读 AstrBot 源码 `CommandFilter.init_handler_md` 定位）**：指令 handler 签名里的
可变参数 `*extra: str` 会被 AstrBot 当成一个**没有默认值的必填参数**（它只遍历
`signature.parameters`，`*extra` 的 default 是 empty、注解是 str）——
所以哪怕 `/清缓存 全部` 把 `kind` 填上了，校验也会卡在 `extra` 上。
**凡是用了 `*extra` 的指令全都中招**：本插件共有 5 个（/清缓存、/推送测试、
/提醒测试、/群备注、/名言）。

**修法**：换成 AstrBot 官方的贪婪参数写法
`extra: GreedyStr = GreedyStr`（`from astrbot.core.star.filter.command import GreedyStr`）——
AstrBot 会把指令后面剩余的所有词合并成一个字符串传进来，空参时给空串，
行为与原来完全一致（`/推送测试 计科2201 软工2301` 多关键词照常）。
默认值写**类本身**而不是实例，是因为 AstrBot 靠 `default is GreedyStr` 识别贪婪参数；
直接函数调用（离线测试）没传参时拿到的是类对象，由 `_greedy()` 统一洗回空串。

测试：新增 K7（5 个指令签名逐个盯：无 `*可变参数`、末参必须是 GreedyStr）与
K8（按 AstrBot 校验逻辑**逐行复刻**，直接验证 `/清缓存`、`/清缓存 全部`、
`/推送测试 词1 词2`、`/群备注 2301 软工 2301班` 都能通过参数校验）。

## 1.7.0 更新说明：CF 头像「查不到」的真正原因

> 需求原话：「头像还是查不到啊，我看好多都是用 qq 头像的，真没有办法吗」

这次先把「CF 头像到底能不能下」实测清楚了 —— 结论跟 1.5.0 的判断**相反**。

### ① 实测：CF 的大图头像是**源站坏了**，不是缓存问题

拿 8 个真实账号（tourist / Petr / Benq / ecnerwala / ksun48 / Um_nik / maroonrk / neal）两轮实测：

| 候选 | 尺寸 | 成功率 | 备注 |
|---|---|---|---|
| 大图地址 | ~300px | **4/8** | 大面积 503，而且多轮都不恢复 |
| 小图地址 | 69×80 ~ 76×80 | **8/8** | 唯一可靠的 CF 真头像源 |

再逐条排除「是不是我们这边的问题」：

| 换什么试 | 结果 |
|---|---|
| 换 UA（浏览器 / curl） | 还是 503 |
| 加 `Referer: https://codeforces.com/` | 还是 503 |
| 换代理出口 / 直连 | 还是 503 |
| **加 `?v=<时间戳>` 换 CDN 缓存键** | 响应头标记**确实回源了** → **还是 503** |
| 试 `/big/`、`/medium/`、`/small/` 路径 | 全 503 |

最后两行是关键：**1.5.0 判定的「Cloudflare 把上游故障期的 503 缓存了 2 天、穿一次就能拿到」不成立** ——
真回源了源站照样 503。所以 1.5.0 加的「穿缓存」那一枪（每张卡多等 2.5 秒）**纯属白等**，1.7.0 已删除。

### ② 那「头像查不到」的病根在哪？—— 串行取图把预算吃光了

1.5.0 的取图是**串行**的：先试大图（1.1s，失败）→ 再打穿缓存那一枪（2.5s，也失败）→
这时整卡的 5 秒预算已经没了 → **后面那个实测 8/8 都能下到的 `avatar` 小图根本没机会试**。

同一台机器、同一批账号，改前 / 改后对比：

| 账号 | 1.5.0（串行 + 穿缓存） | 1.7.0（并行） |
|---|---|---|
| Petr（title 503） | 3.19s | **1.23s** |
| maroonrk（title 503） | 2.12s | **1.10s** |
| neal（title 503） | — | **1.11s** |
| tourist（都正常） | 1.12s | **1.12s** |

改法：**所有候选并行发起**，谁先成用谁，但给高优先级候选一个 2 秒「让位窗口」——
大图能下就用画质最好的，挂了也完全不拖累小图。

### ③ 那为什么有些方案「看着稳」？

把几种常见做法摆在一起想了一遍，结论是：**「稳」往往不是因为能拿到图，而是因为失败时不出声**。

| 常见做法 | 为什么看起来稳 |
|---|---|
| 头像地址落库，只在首次查询时取一次，之后永远读库 | 之后**再也不请求图床**，自然撞不上 503 |
| 拉到就内联进渲染，拉不到就退回原始地址让客户端自己取 | 从不因头像失败而重试、报错或丢卡 |
| 渲染端（浏览器）自带磁盘缓存 | 命中即零成本 |

所以那种「稳」= **长期缓存 + 失败静默降级 + 永不重试**，并不是真有什么办法能拿到源站已经坏掉的图
（源站该 503 还是 503，只是失败时不报出来，用户看不出来）。

这两条我们能落地：**头像拿到就长期留着**（本地缓存 7 天）、**拿不到也照样出卡**（不重试、不丢卡）。

### ④ 1.7.0 改了什么

> ⚠️ **下面这几条里的 QQ 头像相关内容已在 1.7.2 全部删除**（用户要求「取消 QQ 头像的设置，
> 查不到头像就降级为名字首字母」）—— 保留在此仅为记录当时的排查过程。

| 改动 | 说明 |
|---|---|
| **并行取图** | `_fetch_best()`：所有候选同时发起 + 2s 让位窗口，失败的候选不再拖累整张卡 |
| **删掉穿缓存** | 实测无效（`MISS` 也 503），白等 2.5s 还把预算吃光 |
| **每个通道分预算** | 以前慢通道（代理取 CF 要 1~3s）会把预算耗到超时，后面那条能通的通道根本没机会跑 |
| ~~默认灰图识别~~ | （1.7.2 删除）QQ 头像的 openid 接口对**任何**参数都回 200、内容是 40×40 默认灰图 |
| ~~QQ 头像通路重排~~ | （1.7.2 删除）有真实 QQ 号时优先走 QQ 头像（实测 0.1s 回真图） |
| ~~`profile_avatar_source` 新配置~~ | （1.7.2 删除）`auto` / `qq` / `cf` 三档头像优先级 |
| **次品卡判定** | 没取到平台头像（卡片上是首字母块）才算次品：不缓存档案 + 发完即删 |

### ⑤ 现在的头像策略（1.7.2 定稿）

* 平台头像（大图 → 小图双地址兜底）**并行取**，谁先成用谁；
* 全部拿不到 → **名字首字母圆角块**，下次查询重新联网（图床恢复就能自己好）；
* 没有开关要配 —— 装完即用。

## 1.6.0 更新说明：一键清战绩缓存 + 名言库可视化管理

> 需求原话：「增加一键清除 cf/nk 查询缓存（分开）的指令，需要给出具体清除的数量（不用返回具体内容），
> 比赛缓存不要去动他；名言库支持可视化管理，我要看到全部名言以便不好的东西加进来」

两件事都是「把控制权交回给人」：**发现数据不对时的自救手段**（清缓存），
和**对推送内容做最终把关的手段**（逐条看名言、屏蔽不合适的）。

### ① `/清缓存 cf` / `/清缓存 nk`：分开清、报数量、不碰赛程

```
/清缓存          → 列出各类现有条数 + 用法
/清缓存 cf       → 清 CF（用户档案 + 单场成绩）
/清缓存 nk       → 清牛客（用户档案）
/清缓存 全部     → cf + nk 一起清
/清缓存 题库     → 只清 CF 题库映射（一般不用碰）
```

实机回复长这样（**给了具体条数，但没有任何用户/比赛的具体内容** —— 正是用户要的口径）：

```
🧹 已清除 CF 查询缓存：共 8 条
· CF 用户档案 3 条
· CF 单场成绩 5 条
🗓 赛程缓存（比赛数据）没有动，订阅表 / 提醒记录 / 已推送记录也没动。
📦 现在还剩：CF 档案 0 · CF 单场成绩 0 · 牛客档案 1
```

**为什么必须「分开 + 不碰赛程」**：`profile_cache.json` 里混着四种东西，代价完全不同 ——

| 键前缀 | 是什么 | 清掉的代价 |
|---|---|---|
| `cf:v2:<handle>` | CF 用户档案（10 分钟） | 下次 `/cf` 重新联网，几秒 |
| `cfcs:<cid>:<handle>` | 单场 CF 成绩（24 小时） | 下次查那场重新拉一次 |
| `nk:<uid>` | 牛客档案（10 分钟） | 同上 |
| `cfprob:counts` | **CF 题库映射（全局共享）** | **要重下 2.2 MB** —— 所以它单独一个 `题库` 类别，清 cf 时**绝不**顺手带走 |

赛程缓存是**另一个文件**（`contests_cache.json`，抓取层写的）：清掉它意味着下一次日报
要当场重新联网抓一遍所有平台，代价高且完全没必要 —— 所以 `/清缓存` 的任何分支都碰不到它
（测试里有一条断言专门盯这个：清三类缓存前后 `load_contests()` 的返回值必须逐字节相同）。

为什么值得有这条指令：战绩缓存是**头像、rating 曲线、单场成绩**这些可选内容的快照。
第三方接口抽风或改版时，缓存里那半截数据会一直显示到 TTL 到期，看着就像「插件坏了」；
清一次立刻重查，是最快的自救手段。面板 ⑤「缓存维护」区也有同样的按钮（三行分列条数 + 各一个「清除」）。

### ② 名言库可视化管理：**全部**名言都列出来，逐条屏蔽 / 新增

面板新增 ④「名言库」（`views/panel/index.html` 的 `#quotes` 区）：

* **列出全部**（内置 62 条 + 你自己加的全部，**含已经被屏蔽的**，被屏蔽的显示为灰色 + 「已屏蔽」标签）；
  每条显示 `〖正文〗 —— 出处`、分类标签、来源（内置 / 自定义），一屏能滚动过一遍；
* **三种筛选**：按分类下拉、按关键词搜（正文与出处，大小写不敏感）、「只看已屏蔽」；
* **屏蔽 / 恢复**：内置句子在代码里改不动，所以「屏蔽」写进单独的黑名单 —— 它不再参与抽取，
  但随时能恢复（"恢复" 后立刻回到抽取池）；
* **新增 / 删除**自定义句子（正文 ≤60 字，可附出处）；空值 / 超长 / 重复三种坏输入都会被
  当场拒掉并说明原因（重复检测是对**整个库**做的，避免同一句在池里占两个名额、概率翻倍）。

屏蔽名单与自定义句子都存在 **`data/quotes.json`**，与配置项 `daily_quote_extra` 合并去重
（两处都能加，加起来算）：

```json
{
  "schemaVersion": 1,
  "custom":  [{"text": "补题是比赛真正开始的地方。", "by": "协会"}],
  "blocked": ["builtin:a55a660c39"]
}
```

`blocked` 里存的是 **`正文 sha1 前 10 位`**，不是「第几条」：内置库将来增删句子时下标会整体错位，
用户的屏蔽记录会莫名作用到别的句子上；用正文散列则「正文不变、id 不变」。

指令侧也同步了：`/名言 库` 现在报「共 N 条（可抽取 M 条，已屏蔽 K 条）」，被屏蔽的标 🚫，
并提示去面板逐条管理；`/名言 <关键词>` 的搜索**不返回已屏蔽的句子**（搜出来也用不了，徒增困惑）。

### ③ 顺手修正的一处旧行为

1.4.0 的配置说明写着「自定义名言与内置库混在同一个池里抽」，但当时的实现只有在
`daily_quote_cats` 里**额外写上 `custom`** 才真的生效 —— 也就是默认配置下自定义句子
**根本抽不到**。1.6.0 改成「自定义恒进池」：不想要某一句就在面板里删掉/屏蔽它。
（测试 `名言库②` 里专门有一条断言盯这个：默认三类开着时，自定义句子必须能被抽中。）

## 1.5.0 更新说明：CF 头像的 503 是「CF 自己坏了 + CDN 帮你缓存了 2 天」

> 需求原话：「如 cf 头像依旧有部分查询不到 优化（然后未查询到的 cf 头像的战绩卡不要缓存，发完就删）」

### ① 先说结论：换通道、换尺寸、换 URL 都没用 —— 是 CF 图床自己 503

用一场真实比赛（Educational Round 195，7881 名参赛者）里**跨榜单抽样 36 个账号**实测。
先看总表：

| 探测方式 | 结果 |
|---|---|
| 大图地址 | 25 张成功 / 11 张 HTTP 503 |
| 小图地址（**另一个地址**） | **同样那 11 个账号失败** —— 失败是**按账号**固定的 |
| 走系统代理出口 vs 直连（不走代理） | **一模一样**，跟我们的网络通道无关 |
| `?v=<时间戳>` 穿缓存 | 响应头标记真的回源了，**仍然 503** |
| 加 `Cache-Control: no-cache` / `Pragma: no-cache` | 一模一样 |
| 换尺寸路径（`/300/`、`/original/`、`/avatar/`、`/medium/`） | 全部 503 |
| `http://` 明文 | 403（CF 本来就不让） |
| 第三方图片代理 | 从这台机器**根本连不上**，不可用 |

**把成功/失败拆开看，规律干净得吓人：**

| 账号类型 | 成功 | 失败 |
|---|---|---|
| 有**自己上传的头像**（专属图片地址） | **0** | **11** |
| 没传过头像、用 CF 的**全局共享占位图** | **9** | **0** |

也就是说：那一刻**「有头像的同学反而全都刷不出头像」**，而显示 CF 默认灰头像的同学一切正常。
原因是那 11 张**用户专属**图片在 CDN 里没有副本 —— CDN 根本没回源，直接端出上次缓存下来的
那张 503；而占位图全世界共用一个地址，CDN 里一直有。

这个 503 的响应头信息量很大，三条最关键：

- 缓存策略写着 **max-age=172800** —— 这张 503 被缓存了**两天**；
- 缓存状态标为**陈旧副本** —— 端出来的是 CDN 里存着的那一份，不是现取的；
- 服务端计时里**回源耗时是 0** —— 根本没去问源站。

**「回源耗时 0」是关键**：CDN 没去问源站，直接把上次那张 503 端了出来。
也就是说 —— CF 图床**短暂抽风的那几分钟里产生的 503，会被 CDN 缓存 2 天**；
源站早就恢复了，用户还是要连着两天看不到头像，同一地址怎么重试都一样。

### ② 对策：503 时「穿一次缓存」，别坐等 2 天

`core/card.py` 新增 `_bust_url()` + `_read_once()`：拿到 **503** 时，用一个带时间戳参数的
地址（`?v=<now>`）再打一枪 —— 换个缓存键就绕过了那张陈旧 503，能直达源站。

- 源站已恢复 → **当场拿回头像**（并且照常存 7 天本地缓存，之后不再碰 CDN）；
- 源站还在抽风 → 1.7.0 起不再白等（那套「穿缓存」已删）：并行取图会直接落到能用的 `avatar` 小图；
- **只有「秒回的 503」才多打这一枪**（实测缓存副本约 0.7~1.1s 返回）：回得慢说明
  已经问过源站了，再穿一次没意义；
- **一枪不够就歇 5 分钟（全局冷却）**：穿缓存失败说明源站此刻真坏了，没必要让后面
  每个同学都陪着等 —— 实测不加这条时，图床故障期间每次 `/cf` 要多等 **10~12 秒**；
- 403/404 这类「地址本身不存在」的硬失败立刻放弃，超时/连接被拒则换通道
  （代理 ↔ 直连）—— 四种失败处理得明明白白。

顺手把取图的超时与体积参数收紧了一轮：

| | 旧 | 1.5.0 |
|---|---|---|
| 单张头像超时 | 8s | **4s** |
| 整张卡所有头像候选的总预算 | 14s | **5s** |
| 响应体上限 | 4 MB | **2 MB** |
| 失败后多久再试 | 30 分钟 | **15 分钟**（图床恢复后更快自动复原） |

实测（同一批账号，图床故障期间）：单张头像最坏耗时 **10.7s → 5.9s**，
典型失败路径只要 **约 2 秒**（两次秒回的 503）。

还加了 `_looks_like_markup()`：图床抽风时**状态码可能仍是 200 却回一页 HTML**，
直接交给 Pillow 只会报「cannot identify image file」，判别一下能说清是「图床回了网页」。

> 顺带一个发现：36 个抽样账号里有 **16 个**的头像地址指向 CF 的**全局共享**占位图
> （他们从没上传过头像，CF 就一直给这张默认图）。
> 这类地址全世界共用一个缓存键，本地磁盘缓存命中后基本零成本；卡片上显示的就是 CF 官网
> 那个默认灰头像，和官网一致。

> 📌 一句话总结：**这部分我们改不掉 CF，但能把「CF 抽风 5 分钟」造成的
> 「用户 2 天看不到头像」缩回到「下一次查询就能拿到」。**

### ③ 没取到平台头像的那张卡：不缓存、发完就删（用户明确要求）

「未查询到的 cf 头像的战绩卡不要缓存，发完就删」，落成两条动作：

1. **档案不进缓存**：渲染完若头像没拿到，就把这份档案从 `profile_cache.json` 里删掉
   （`ProfileFetcher.forget()` / `Store.delete_profile_cache()`）。缓存里存的正是那份
   「带着当下取不到的头像地址」的档案，留着它下次查询还是同样结果；删掉后下次会重新联网，
   图床一恢复就能自己好起来。
2. **卡片图发完即删**：这张卡的文件在消息发出后立即删除（`_profile_output` 的 `finally`
   分支，发图成功、回退纯文本、发送抛异常三种情况都删）—— 它下次一定会重新渲染，留着只占磁盘。

判定口径：渲染层通过 `info["avatar_source"]` 上报头像来源 ——
`platform`（拿到了平台头像）/ `placeholder`（只剩首字母块）。
**1.7.2 起只剩这两态**（`qq` 那一档随 QQ 头像链路一起删掉了），只有 `placeholder` 算次品。

- 开关：配置项 **`ephemeral_card_without_avatar`**（默认开）。关掉就回到老行为：
  照常缓存、卡片留在 `cards/` 里等定期清理。
- 代价：这类用户每次查询都要重新联网 —— 可以接受，反正它本来就取不到头像。
  而且 `_AVATAR_FAIL_TTL`（15 分钟）限住了对图床的重试频率。

### ④ 这一轮定下的取图策略

把上面几轮实测的结论收敛成下面这套规则，全部由插件自己实现：

| 策略 | 我们的实现 |
|---|---|
| 头像多候选、**并行**取 | 大图失败不再拖累整卡：候选并行发起，谁先成用谁（见 ②） |
| 超时按「候选」算，**不按「整卡」算** | 单候选 6s、高优先级候选 2s 让位窗口、整卡总预算 8s（并行发起，不叠加） |
| 响应体限流 | 单张头像上限 2 MiB，超了直接判为坏数据 |
| **拉不到也照样出图** | 平台头像取不到就画**首字母块**，**永远有图**，不重试、不丢卡 |
| 拿到就长期留着 | 本地缓存 7 天，热路径零网络 |
| 取不到时**主动清缓存** | 与「长期缓存」配套：这类档案不留缓存、卡片发完即删（见 ③），下次重新取 |
| 对上游限速 | 错峰并发 + 全局查询锁，避免打爆数据源 |
| 用户资料按需拉取 + 落盘缓存 | `profile_cache.json`，默认 10 分钟 |

### ① 「每天换一句」是怎么定的：按天抽、同一天稳定

## 1.2.21 更新说明：磁盘缓存按体积自动「削峰」+ 清理彻底摘出日报链路

> 本版把 1.2.20 的缓存治理一次做透：阈值按你实际扩到的 **1.5 GB** 盘重新标定，
> 并新增「磁盘余量保护」与「清理独立成后台任务」。

**背景**：卡片图与头像都缓存在 `data/.../cards/` 下，长期运行只会越攒越多（头像一张几百 KB、
卡片图几十 KB）。原来只按「保留 30 天 + 每目录最多 500 个文件」清 —— 这两把尺子都管不住
「文件都不老、数量也没超、可单个特别大」的情形；小盘机器上更怕的是**盘被吃满**。

### ① 体积兜底：两个触发条件，取先到者

| # | 触发条件 | 为什么需要 |
|---|---|---|
| ① | `cards/`（含 `avatar_cache/`）总占用 **>** `card_cache_max_mb`（默认 **512 MB**） | 缓存自己涨太多 |
| ② | 所在卷剩余空间 **<** `card_cache_min_free_mb`（默认 **300 MB**） | 盘快满了 —— 即使缓存没到自己上限也要腾地方 |

命中后一律按 **最早写入优先** 删，直到降到 **80% 水位**。触发 ② 时预算会压到
「当前体积 − 缺的那部分」，必要时把图片缓存清空 —— 缓存都能重建，盘写满才是真事故。

**1.5 GB 的盘怎么算的**：缓存最多 512 MB（约 1/3）＋ 随时预留 300 MB，
剩下约 700 MB 留给 AstrBot / Python / 日志。盘更小就按「总量 × 1/3」和「总量 × 20%」等比缩。

### ② 清理不再碰日报（用户明确要求）

> 「清理操作不得干扰日报主体工作，不得影响当前任务或者当前指令」

清理从主循环里**摘了出来**，跑在自己的后台任务上：

| 保障 | 做法 |
|---|---|
| 不拖慢日报/提醒 | 清理**不跟**抓取 / 日报 / 提醒串行（它们是主循环，清理是独立 task）。清几千个文件花十几秒也只拖慢自己 |
| 不会弄丢日报记录 | 只删**可重建的缓存文件**，从不碰 `subscriptions.json` / `sent_log.json`，也不推任何消息 |
| 不打断正在跑的指令 | 有 `/cf`、`/nk` 在渲染卡片时，整个 `cards/` 清理**让路**到下一轮 |
| 不碰刚生成的文件 | 只删「最后写入超过 5 分钟」的缓存；刚生成、可能正在被读取或马上要发出去的一律不动 |
| 出问题也不连累本体 | 清理 task 内部吞掉所有异常，绝不让它影响调度循环

日志会长这样：

```
[contest_daily] 缓存体积兜底（缓存 540 MB 超过上限 512 MB）：已按「最早写入」删除 832 个文件、释放 122 MB，现约 418 MB，磁盘剩余 402 MB
[contest_daily] 缓存体积兜底（磁盘只剩 96 MB，低于预留 300 MB）：已按「最早写入」删除 61 个文件、释放 88 MB，现约 12 MB，磁盘剩余 184 MB
[contest_daily] 缓存清理：战绩 3 条 / 提醒记录 12 条 / 卡片图与头像 893 个文件（其中体积兜底释放 210 MB）
```

真的腾不出空间时（盘被别的文件占满）会**明确告警**，而不是默默失败：

```
[contest_daily] 磁盘剩余仍只有 96 MB（没到预留的 300 MB）—— 图片缓存已经清光了，空间是被别的文件占着的，请手动清理磁盘
```

### 其它细节

- 排序键是文件的**最早写入时间**（缓存文件写完就不再改动，等价于「最早创建」），
  这样跨平台语义一致 —— Linux 上没有真正的「创建时间」
- 删到 80% 水位而不是「刚好卡在上限」：留缓冲，免得删完立刻又被下一轮触发
- 被删的都是**可重建**的东西：卡片图下次查询重新生成、头像重新下载，只是慢一点，功能不受影响
- `card_cache_max_mb` 填 `0` 可关掉第 ① 条；`card_cache_min_free_mb` 填 `0` 可关掉第 ② 条（都不建议）
- 清理节奏受 `cache_cleanup_minutes`（默认 30 分钟）控制

> 💡 **这是磁盘占用，不是进程内存**。这两类缓存是落在硬盘上的文件，不会常驻 AstrBot 进程。
> 想压**进程内存**请调 `profile_status_count` / `upcoming_days` 这类「一次拿多少数据」的参数
> （见下面的「小内存部署建议」）。

## 1.2.19 更新说明：修好 CF 头像 + 拦下「emoji / 中文 handle 查错人」

**用户反馈**：① 这版爬不到 CF 头像了（以前可以）；② 非字母数字的 handle 查不了，比如一个 emoji 笑脸。

### ① CF 头像：不是「爬不到」，是「直连不通」

| 牛客站点 | 0.2s ✅ | 0.1s ✅ |

三个模块都写死了 `ProxyHandler({})`（强制直连、不读系统代理）。CF API 和牛客直连没问题，
但**头像 CDN 挂在 Cloudflare 上，这台机器只有走代理才通** —— 于是一张头像都拿不到，
卡片只能画灰色占位图（后来 1.2.9 补过 QQ 头像兜底，1.7.2 已按用户要求删掉）。

  最坏要 **36.7s** 才吐占位图（用户实测），现在冷启动实测 **1.2s** 就拿到头像。

### ② emoji / 中文 handle：CF 会把它删掉再查**别人**

逐个字符实测 CF 的口径 —— **只允许 `[A-Za-z0-9_.-]`，其余一律先删掉**：

> 同一句文案**，上面的详细原因只写进 AstrBot 日志。想让群里直接看到原因，把那个配置关掉即可。

## 1.2.18 更新说明：修复「负分选手查出来是暂无」

**用户反馈**：`/cf _I_AM_THE_LOWEST_` 这个号当前 Rating 是 **-35**、最高 **775**，卡片却渲染成「暂无」。

### 根因：Codeforces API 对 rating ≤ 0 的用户**整个省掉** rating 字段

实测（2026-10-16）这个 handle 的两个接口：

| 接口 | 返回 |
|---|---|
| 用户信息接口 | 只有 handle / country / 头像地址……**没有 rating / 最高 rating / 段位这三项**（不是 0，是压根没有） |
| 比赛记录接口 | **26 场完整记录**：当前 **-35**、历史最高 **775** |

CF 的口径是「没有 rating 字段 = 未定级」，而负分恰好触发了这个省略 —— 所以插件把一个打
了 26 场 rated 的选手当成了没打过的人。之前的代码只认用户信息接口，就显示成「暂无」。

### 修复：用本来就拉过的比赛记录兜底（零额外请求）

「比赛记录」是「本周战绩」一直都在拉的数据，现在顺手多算一个**全历史汇总**：

* rating 为空时取比赛记录最新一场的 rating 值（→ -35）；
* `max_rating` 为空时取全历史的最大值（→ 775）；
* 段位 / 最高段位为空时按 CF 官方分段自己推（-35 → **newbie**，卡片徽章不再空着）；
* `extra.rating_derived` 标记这次兜底是否发生（留文案用），`extra.rated_contests` 记参赛场次。

### 顺带修的：旧缓存不会自己更新

战绩缓存是**落盘**的（`profile_cache.json`），旧条目里存的就是 `rating: None`，改了取数口径
它也不会自己失效。所以缓存键加了版本号前缀（`cf:v2:<handle>`）—— 升级后第一次查会重拉一次，
保证立刻看到正确结果。以后再改取数口径同样只动这个版本号。

* 新增 10 条解析层用例（汇总解析 / 乱序 result / 空历史 / 分段边界 1199→3000 / 非数字）
* 新增 6 条端到端用例（mock 一个「info 没有 rating 字段」的用户 → rating -35、max 775、newbie、正常渲染）
* 真实账号实测：`_I_AM_THE_LOWEST_` → Rating **-35**、最高 **775**、徽章 **最高 Rating 775 / newbie**

## 1.2.17 更新说明：改推送时间就重测一遍 + 「立即推送测试」面板

**用户原话**：*「时间一旦更改后，刷新今天的推送状态到 0，其他已将发过的群也要重新测试；添加立即推送的测试按钮到设置里！」*

这句话正好接上 1.2.15 留下的坑：他在 1.2.15 之后把 `daily_time` 改到 12:42，结果
**三个群全无反应** —— 因为其中两个群当天已经成功收到过日报，被「今天已发过」的记录静默跳过了。
他要的不是「只补试没成功的」，而是**改完时间就该把所有群都重测一遍**（他正在调群权限，需要看到每个群的真实结果）。

这一版把两件事都做了。

### ① 改了 `daily_time` → 当天「已推送」记录清零 → 所有群重收一遍

| | 1.2.15 / 1.2.16 的行为 | 1.2.17 的行为（默认） |
|---|---|---|
| 你改了 `daily_time` | 只补试**没成功**的会话，已收到的群**跳过** | 当天记录**全部清零**，**所有**订阅群重新收一遍 |
| 改后的时间点已经过了 | 立刻补跑一轮 | 立刻完整重跑一轮 |
| 想回到旧行为 | —— | 把配置项 `daily_reset_on_time_change` 关掉 |

判定依据是**存盘的**时间指纹（`sent_log.json` 里的 `dailyTime = {date, time}`），不是内存变量 ——
在 AstrBot 里保存插件配置往往会重载插件，内存标记会被清空，只靠内存会漏判。两条安全边界：

* 只在「指纹日期 == 今天」时才算「改了时间」。指纹是昨天的说明今天还没跑过任何一轮，根本没有
  「今天的已推送记录」需要清；
* 清算后**立刻**把新时间写回指纹，保证这次变更**只清算一次**，不会每个 30 秒的 tick 都清一遍。

> ⚠️ 代价要知道：改时间会让**当天已经收到日报的群再收到一条**。这正是用户要的（他在验证权限），
> 但如果你只是随手调一下时间、不想打扰大家，就把 `daily_reset_on_time_change` 关掉。

日志里会明确写出来，方便对照：

```
[contest_daily] 检测到日报时间从 09:00 改为 12:42，已把「2026-10-16 已推送」的 2 条记录清零
                —— 所有订阅会话都会重新收一遍日报
[contest_daily] 日报已推送 3/3 个会话
```

## 1.2.16 更新说明：找到「两个群能收到、第三个收不到」的真正原因——群里的开关

**用户实测**：调完权限配置后 2 个群能收到主动消息了，第 3 个群一直失败（12:53 那轮日志：
`日报已推送 0/3 个会话，1 个被平台拒绝主动消息`）。用户的原话是「权限配置是一样的」——
这句判断本身没错，但**漏掉了一个不在开放平台里的开关**。

### 根因：`机器人主动在群聊内发言` 是**每个群单独设置**的

AstrBot 官方接入文档（`docs.astrbot.app/platform/qqofficial/websockets.html`）原文：

> **设置机器人可获取的群聊消息范围和主动发言**
> 在手机 QQ 的群聊设置中打开机器人设置，推荐将「机器人可获取的群聊消息范围」设置为
> **获取群内全部消息**，并开启 **机器人主动在群聊内发言**。
> 这样机器人可以接收群聊全量消息，也可以在群聊中主动推送消息，例如定时任务推送、插件主动通知等。

**它是群里的设置，不是开放平台的配置**，所以会出现：

- 开放平台那边「权限配置一模一样」✅ —— 你的判断是对的
- 但每个群要在**手机 QQ → 打开该群 → 群设置 → 机器人 → 选中这个机器人**里，
  各自打开「机器人主动在群聊内发言」
- 只开了 2 个群 → 就是「2 个能收到、第 3 个收不到」

顺带：同一个位置建议把「机器人可获取的群聊消息范围」设为**获取群内全部消息**，
否则机器人只能收到 @ 它的消息（本插件的 `/日报`、`/赛程` 都靠 @ 触发，所以不影响，
但以后想做「群内关键词响应」就会受限）。

### 这次改的

| 改动 | 说明 |
|---|---|
| `PUSH_PERM_HINT` 重排排查顺序 | **① 群里的开关**（最常见、最可操作）→ ② 机器人是否已上线 → ③ 额度说明（不用操心）→ ④ 被动通道兜底。之前把「查上线」放在第一位，把最常见的群开关漏掉了 |
| 故障排查章节同步 | 排查第 4 条也改成先查群里的开关 |
| 测试关键字更新 | 提示文案必须包含「群设置」「机器人主动在群聊内发言」「每个群单独设置」 |

### 排查「某个群收不到」的完整顺序（1.2.16 起）

1. **手机 QQ → 打开该群 → 群设置 → 机器人 → 选中本机器人 → 打开「机器人主动在群聊内发言」**
2. 看日志汇总行的**分母**：`0/3` = 三个群都在订阅表（是推送失败）；分母少了 = 那个群没订阅成功，去群里发一次 `/订阅日报`
3. 按错误码判断：
   - `40034101` / `40054003` 机器人不是群成员 → 机器人被移出该群了
   - `40034102` / `40034105` 无权限 → 见上面第 1 步；另外 **QQ 用户也可以在客户端单独关闭「接收主动消息」**
     （官方原文：*「如果设置了关闭，主动消息一律发送失败」*）
   - `40034024` / `40034005` msg_id 无效或已过期 → 被动回复超时了
   - `40054016` 机器人已下线

## 1.2.15 更新说明：改了推送时间/权限之后「为什么还是不推」的两个坑

**用户实测反馈**：调完权限设置后 2 个群能收到主动消息了（说明权限这条路走通了），
第 3 个群收不到；随后把推送时间改到 12:42，**三个群全都没反应**，问「是一天只发一次吗」。

### 回答：是，而且「一天一次」有两层

| 层 | 记录在哪 | 作用 |
|---|---|---|
| 整轮一天一次 | 内存 `_last_daily_key` | 今天跑过这一轮就不再跑（这是为了防止失败的会话每 30 秒重试一次） |
| 每个会话一天一次 | **存盘** `dailySent[umo]` | 该会话今天成功发过就跳过，**插件重启也仍然有效** |

副作用就是：把 `daily_time` 改到「今天还没到的点」、再等到点，也**不会有任何反应**——
被「今天已经跑过一轮」的标记挡住了。这正是 12:42 三个群都没动静的原因。

### 这次修的两处

| 修复 | 说明 |
|---|---|
| **改 `daily_time` 立刻生效** | 时间配置一变就再放行一轮（新增 `_last_daily_time` 参与判断）。有存盘记录兜底，**今天已成功的群不会被重复打扰**，只有没送出去的会话会被再试一次 |
| **汇总行点名「谁没收到」** | 以前只有 `日报已推送 2/3 个会话，1 个被平台拒绝主动消息` 一个数字；而 perm 的详细提示**每天只打印一次**，当天第二轮之后再失败就**根本查不出是哪个群**。现在汇总行直接列出未送出的会话，并区分「被平台拒绝 / 临时故障 / 今天已发过、跳过」 |

日志现在长这样（每天一条）：

```
[INFO] [contest_daily] 日报已推送 1/4 个会话，1 个被平台拒绝主动消息（详见上面的提示）、
       1 个临时故障、1 个今天已发过、跳过；未送出：default:GroupMessage:xxxx、default:GroupMessage:yyyy
```

### 排查「某个群收不到」的正确姿势

1. 先看上面那一行的**分母**：
   - 分母 = 订阅数 → 那个群在订阅表里，是**推送失败**，按紧随的错误码定位（见下）
   - 分母少了 → 那个群**压根没订阅成功**，去群里发一次 `/订阅日报`（用 `/订阅列表` 可直接核对名单）
2. 按错误码判断：
   - `40034101` / `40054003` 机器人不是群成员 → 机器人被移出该群了
   - `40034102` / `40034105` 无权限 → 该会话侧没放开主动消息。注意 **QQ 用户可以单独关闭「接收主动消息」**
     （官方文档原文：*「QQ 用户可以在 QQ 客户端主动设置是否接收机器人发送的主动消息，如果设置了关闭，
     主动消息一律发送失败」*）——这类群从机器人这边改设置也救不回来
   - `40054016` 机器人已下线
3. 想**当天再试一次**：把 `daily_time` 改成当前时刻（1.2.15 起立刻生效），
   或在 AstrBot 里重载一次插件 —— 两种方式都只会补试没成功的会话，不会给已收到的群重复发

> ⚠️ 1.2.17 起上面第 3 条**语义变了**：改 `daily_time` 会先把当天「已推送」记录清零，
> **所有**订阅群（包括今天已经收到过的）都会重新收一遍。想把手动重测做成一键操作，
> 用「推送测试」面板的按钮，或群里发 `/推送测试`；想回到旧行为就把 `daily_reset_on_time_change` 关掉。

> ⚠️ 1.2.16 补充：这一节漏了最关键的一条 —— **「机器人主动在群聊内发言」是每个群单独设置的**，
> 见下一节。如果你遇到「有的群能收到、有的群收不到」，先去群里把这个开关打开。

## 1.2.14 更新说明：把「主动消息被拒」的排查口径写清楚（并更正 1.2.13 的一处说法）

**起因**：用户质疑——「官方给个人认证的机器人有 30/qpm 的额度啊」。

这个质疑是对的。1.2.13 的说明把两件事说混了：**频控额度 ≠ 权限是否授予**。
有额度，说明这项能力存在；但「能不能发」是另一个问题。

### 先分清两个错误码（官方《发送群聊消息》接口文档的错误码表）

| 错误码 | 官方描述 | 实际含义 | 该怎么办 |
|---|---|---|---|
| `40034100` | 主动消息发送超过频控限制 | **有**权限，只是发太快 | 降低频率，等额度恢复 |
| `40034105` | 主动消息发送失败，无权限（排查建议原文：检查机器人权限设置） | **没**资格发，与条数无关 | 检查机器人的权限 / 上线状态 |

我们日志里出现的是 `40034102`（无权限家族），**不是频控错**。所以
「个人认证有 60/qpm、未认证有 30/qpm」这项额度，推不出「你的机器人现在就能发」。

### 上线之后，额度其实很充足

官方《消息收发概述》与接口文档给出的群聊主动消息频控：

| 认证类型 | Bot 维度 | 单关系维度 | 每日上限 |
|---|---|---|---|
| 企业认证 / 个人身份证认证 | 60/qpm | 20/qpm | 1000 条/群 |
| 未认证 | 30/qpm | 20/qpm | 1000 条/群 |

日报一天 1 条、赛前提醒一天几场（每群每天上限 1000 条），**远远用不满**。
换句话说：**卡点不在额度，在权限 / 上线状态**。

### 更正后的排查顺序（插件日志里打印的就是这段）

1. **先看机器人是否已上线** —— 官方发布流程原文：「提交审核，**审核通过并手动上线后**，
   方可在 QQ 客户端添加机器人至对应场景」。仍处沙箱期的机器人能力受限，主动消息通常发不出去。
2. 上线后按上表的额度走，正常使用完全够。
3. 上线前用**被动通道**：群成员 @机器人 发 `/日报`、`/赛程`，这条路一直不受限制。
4. 也可试**私聊订阅**：把「订阅日报」权限档设为「所有人」，让成员私聊机器人发一次 `/订阅日报`。

> ⚠️ 1.2.13 写的「机器人默认不授予主动消息权限，只能去申请」措辞过强，本节更正为
> 「先确认是否已上线」。另外，**AstrBot 适配器侧的结论不变**：所有插件都走同一个
> `qq_official` 适配器出口，换 API、换推送插件都绕不过去（详见 1.2.13 的源码证据）。

### 这次代码改了三个地方

| 改动 | 为什么要改 |
|---|---|
| **频控不再被误判** | 频控文案「主动消息发送超过频控限制」里**也含「主动消息」四个字**，原来的正则会把 `40034100` 当成永久拒绝 → 立刻放弃重试，还会打印一段错误的「无权限」排查提示。现在先排除频控（`_RE_RATE_LIMITED`），归类为可重试的 `other` |
| **提示与模块文档更新** | `PUSH_PERM_HINT` 换成上面的排查顺序；模块文档注明「换 API 绕不过同一适配器」 |
| **订阅文案会话感知** | `/订阅日报`、`/退订日报` 在私聊里不再说「本群」，改说「本会话（私聊）」——私聊正是备选出路之一，文案得对得上（群里文案不变） |

## 1.2.13 更新说明：定时推送被平台拒绝时，不再刷屏也不再无效重试

**现象**（用户反馈的日志）：每天定时那一下满屏红字 ——

```
[INFO]  qqofficial.platform_adapter:682: 回复消息发送失败: 主动消息失败，无权限，尝试使用主动发送接口
[ERROR] astrbot_plugin_contest_daily.main:450: 推送到 default_xxx:GroupMessage:... 失败:
        ServerError: 主动消息失败，无权限 ...
[INFO]  astrbot_plugin_contest_daily.main:953: [contest_daily] 日报已推送 0/3 个会话
```

**根因不是插件 bug**：定时日报 / 赛前提醒走的是**主动消息**，而 QQ 官方机器人默认不授予
该权限（错误码 `40034102`）。查 QQ 开放平台文档确认：主动消息需单独申请（沙箱期只能在
「沙箱管理 → 消息列表配置」里把自己加进去）；而**被动消息**（用户 @ 机器人后的回复）
群聊有 5 分钟窗口、每条最多回 5 次，**一直可用** —— 所以群里 `/日报`、`/cf`、`/nk`
全都正常，只有定时推送全军覆没。这是平台限制，插件绕不过去。

**这次改的是「被拒绝之后怎么办」**：

| | 之前 | 现在 |
|---|---|---|
| 日志等级 | 每个会话一条 `ERROR`（3 个群 = 3 条红字） | 平台拒绝降为 `WARNING`，**每天只提示一次**，之后降为 `debug` |
| 提示内容 | 只有一句「属平台限制」 | 给出**可操作的解决办法**（申请权限 / 走被动通道） |
| 赛前提醒 | 每 30 秒一个 tick 一直重试：15 分钟窗口内同一场最多重试 **30 次** | 平台拒绝**立即放弃**；其他故障最多重试 **3 轮**后放弃 |
| 启动预检 | 无 | 检测到 QQ 官方机器人**且已有订阅**时，启动日志里提前说清楚 |

现在的日志长这样（三条变两条，且只出现一次）：

```
[WARNING] [contest_daily] 推送到 default_xxx:GroupMessage:... 被平台拒绝：ServerError: 主动消息失败，无权限
[WARNING] [contest_daily] 这是 QQ 官方平台的限制，不是插件故障：机器人默认不授予「主动消息」权限，
          定时日报 / 赛前提醒必然发不出去。可用办法：① 登录 QQ 开放平台申请主动消息权限
          （沙箱期可在「沙箱管理 → 消息列表配置」里把自己加进去）；② 群成员随时 @机器人
          发送 /日报 手动获取，这条被动通道不受影响。（本提示每天只打印一次…）
[INFO]    [contest_daily] 日报已推送 0/3 个会话，3 个被平台拒绝主动消息（详见上面的提示）
```

> ⚠️ 这一节写的「只能去申请主动消息权限」措辞过强，**以 1.2.14 的排查口径为准**：
> 先确认机器人是否已上线，上线后额度很充足（个人认证 60/qpm）。
> 上线之前，让群友 @机器人 发 `/日报` 是最可靠的获取方式（被动回复，不受限制）。

## 1.2.11 更新说明：日报的「未来赛程」与 `/赛程` 指令彻底区分开

1.2.10 把两处统一成了同一个「不含今天」的窗口，用户反馈要**区分开** —— 这两件事
本来就是不同场景，现在各有一套口径、各有一个天数配置：

| | 起算日 | 天数配置 | 为什么这样 |
|---|---|---|---|
| **日报末尾的「未来 N 天」区块** | **不含今天**，明天算第 1 天 | `lookahead_days` | 今天的比赛正文里已按平台列过，再列一次就是重复 |
| **`/赛程 N` 指令** | **含今天剩余**，今天算第 1 天 | `upcoming_days` | 手动查赛程时最关心的是「今晚还有没有比赛」 |

两者都是**自然日、左闭右开**窗口，但用的是两个独立函数
（`_daily_future_window()` / `_query_future_window()`），**不要合并**。

### 天数配置也拆开了

以前 `lookahead_days` 一个值同时管日报区块和 `/赛程` 的默认天数 —— 想调日报的天数
会顺手把 `/赛程` 也改掉。现在新增 **`upcoming_days`**（`/赛程` 专用），
`lookahead_days` 只管日报区块。

## 1.2.7 更新说明：修复「设置了明日赛事，回答里却没有」

**原因**：区块模板 `daily_upcoming_section` 只写了标题 `— 明日赛事 Tomorrow —`，
**漏了 `{items}` 占位符** —— 渲染出来自然只有标题，比赛一条都不显示（数据是全的，
实测周六 22:35 的 WorldQuant Round 1 确实抓到了）。这类「看着像坏了、其实少个占位符」
的坑不值得自己排查，现在直接兜住：

- **漏写 `{items}` 时自动补在末尾**（`daily_section` / `daily_upcoming_section` /
  `profile_week_section` 三处都兜）。模板留空仍然 = 整块不显示（老行为不变）。
- 新增两个占位符：**`{when}`**（`今日`/`明日`/`后天`/`周六`）与 **`{weekday}`**（`周六`），
  放在「未来 N 天」区块里每场前面，一眼知道是哪天。
- 修了一个真 bug：`{when}` 原来按**真实时钟**算相对日期，而不是按日报的渲染时刻，
  跨天边界会算错（15:03 的条目被判成「明日」）。现在跟随渲染基准时间。
- 配置项的 hint 里都补了「必须保留 `{items}`」的提示。

## 1.2.6 更新说明：超时/错误改为静默

- **超时、网络故障、解析异常、插件内部异常一律不回复**，只在 AstrBot 日志里记录
  （日志会标注 `-> 静默不回复`）。原来会回「⌛️ 查询超时了…」「❌ 查询出错…」，

## 1.2.5 更新说明：无效 / 未识别的指令也回同一句

- **无效的指令**（缺参数、参数格式错、查不到该用户）现在回复与**无权限完全同一句**

- **未识别的指令**（@ 机器人 + `/xyz`，任何插件都没注册过）也回同一句，不再沉默；

- **超时 / 网络故障不算无效指令** —— 1.2.6 起改为**静默不回复**（只写日志；`silent_on_error` 可恢复提示）。

## 1.2.4 更新说明：小内存优化（2 GB 进程）+ 回退文本不带提示

- **去掉大 payload 的双重序列化**：解析层以前写 `parse_x(json.dumps(data))`，
  把已解析的 dict 再序列化再解析，多造一份完整对象副本。实测每次拉提交记录
  多花 **+20.9 MB 峰值 / 48 ms**、题库映射 **+9 MB / 19 ms**；现在解析函数
  直接吃 dict，这笔开销归零。取数侧改用 `dict.pop()`，大响应取走即释放。
- **字体实例缓存封顶 24 个**（实测每个字号约 0.3 MB，防止长期运行攒到十几 MB）。
- **新增 `profile_status_count`**：CF 提交记录拉取条数可调（小内存机器建议 3000）。
- **卡片图与头像磁盘缓存纳入定期清理**：超 `card_cache_keep_days` 天（默认 30）
  或超 500 个文件即按最旧的删，避免长期运行攒文件。
- **发图失败回退文本时不再带任何提示语**（按反馈）：用户只看到正常的文本战绩卡，
  失败原因只写 AstrBot 日志。
- README 新增「小内存部署建议」：含各项实测内存占用与 2 GB 机器的推荐配置。

## 1.0.1 修复说明（重要）

**症状**：`/cf`、`/nk` 报 `'Store' object has no attribute 'get_profile_cache'`
（或 `ProfileFetcher` / `fetch_all` 指向了莫名其妙的模块）。

**原因**：插件内部模块原先用 `sys.path.insert(0, 插件目录)` + `from core import ...`
的**绝对导入**。这会把一个**通用名** `core` 塞进全局 `sys.modules`——只要装了另一个
也带 `core/` 包的插件，谁先加载谁赢，本插件的 `core` 就被静默顶替。
而且 AstrBot 重载插件时只清理 `data.plugins.<插件目录名>.*` 前缀的模块，
这个全局 `core` 不在清理范围内，所以**重载也修不好**。

**修复**：全部改为包内相对导入 `from .core import ...`。
AstrBot 是用 `__import__("data.plugins.<插件目录名>.main")` 把插件当**包**加载的，
相对导入既正确又干净。回归测试见 `tests/test_import_isolation.py`。

**升级方式**：直接在 AstrBot 插件页**上传新的 zip 即可**。AstrBot 4.29 对同 `name`
的插件会自动「备份 → 替换 → 重载」，加载失败还会自动回滚，**不需要先卸载**，
订阅与缓存数据（`data/plugin_data/` 下）也不受影响。

| `/订阅列表` | 🔒 管理员 | 查看已订阅的会话（带自定义备注） |
| `/刷新赛程` | 🔒 管理员 | 立即抓取一次 |
| `/推送测试 [关键词…]` | 🔒 管理员 | 推一轮日报测试，验证主动消息权限。带关键词 = **只推给备注/群号匹配的会话**，不打扰其它群 |
| `/提醒测试 [关键词…]` | 🔒 管理员 | 推一轮**赛前提醒**测试（用最近一场比赛渲染，**不写幂等、不影响当天正式提醒**） |
| `/群备注 [关键词] [备注]` | 🔒 管理员 | 给群绑备注，便于面板勾选；不填参数则查看整张映射表 |
| `/清缓存 [cf\|nk\|全部\|题库]` | 🔒 管理员 | 清战绩查询缓存，**回复具体条数**（不含条目内容）；不填参数看各类现有条数。**不动赛程缓存** |

> 🔒 标记的指令默认需授权；**每条指令的权限等级都能在配置里单独改**（见下「权限控制」）。
> 查询类指令默认对所有人开放，也可把 `cf` / `nk` 收紧成仅授权用户，甚至直接关闭某条指令。

## 权限控制

### 每条指令一个权限等级（配置项 `command_permissions`）

在 AstrBot 插件配置的「**各指令权限等级**」里逐条设置，四个等级：

| 等级 | 含义 | 默认给谁 |
|---|---|---|
| `all` | 所有人可用 | `/日报` `/赛程` `/cf` `/nk` `/whoami` `/名言` |
| `admin` | 授权用户可用（AstrBot 管理员 / 白名单 / 群主·群管理员） | `/订阅日报` `/退订日报` `/订阅列表` `/刷新赛程` `/推送测试` `/提醒测试` `/群备注` `/清缓存` |
| `strict` | **仅** AstrBot 管理员与白名单（**忽略**群主 / 群管理员角色） | —— |
| `off` | 关闭该指令，调用时回复无权限文案 | —— |

配置写法（只写想改的，其余沿用默认）：

```json
{
  "赛程": "off",
  "cf": "strict",
  "订阅日报": "admin"
}
```

> ⚠️ 等级写错（比如 `admn`）会**按 `admin` 从严处理**并在日志里提醒一次，不会因为一个错别字放开权限。
> 旧配置项 `admin_only_commands` 仍然兼容：只有 `command_permissions` 里没提到的指令才看它。

### 自定义「无权限」回复文案（配置项 `deny_template`）

默认只回一句鼓励语：

```
前方的功能以后再来探索吧！趁这时间多多刷题哦！
```

想让它带上用户 ID 方便自助申请授权，就改成：

```
前方的功能以后再来探索吧！趁这时间多多刷题哦！\n（你的 ID：{user_id}）
```

可用占位符：`{cmd}` 指令名 / `{user}` 昵称 / `{user_id}` 用户 ID / `{level}` 等级值 / `{need}` 等级说明。
支持字面量 `\n` 换行、全角括号与中文名（`｛指令｝`、`｛用户ID｝`）。

### 回复口径：三种「指令没生效」都用同一句话

按群主要求，用户侧看到的文案是统一的，**具体原因只写 AstrBot 日志**：

| 情况 | 用户看到 | 日志里能查到 |
|---|---|---|
| **无权限**（等级拦住了） | `deny_template` | `拒绝 /cf（等级=admin）` |
| **无效的指令**：没带参数（只发 `/cf`）、参数格式不对（`/nk abc`）、查不到该用户 | 同一句 | `无效指令 /cf（缺少参数）` 等 |
| **未识别的指令**：@ 机器人 + `/xyz`，没有任何插件注册过 | 同一句 | `未识别的指令「xyz」` |
| 查询超时 / 网络出错 / 解析异常 / 插件内部异常 | **静默不回复** | `查询超时… -> 静默不回复` |

三个开关（默认都开）：

- `invalid_reply_like_deny` —— 关掉后「无效的指令」恢复成给用法说明 / 「找不到该用户」提示
- `unknown_command_reply` —— 关掉后「未识别的指令」保持沉默
- `silent_on_error` —— 关掉后超时/错误恢复成可重试的提示（「⌛️ 查询超时了，请稍后再试」）

> 未识别指令的兜底很克制：只处理**被 @/唤醒**且**以唤醒前缀（默认 `/`）开头**的消息；
> 指令名实时读 AstrBot 的 handler 注册表，**别的插件的指令不会被抢答**；
> 读不到注册表时直接沉默（宁可沉默也不误伤）。纯聊天完全不受影响，照常走 LLM。

### 三层判断，任意一层通过即放行（`admin` / `strict` 档生效）

| 层 | 依据 | 说明 |
|---|---|---|
| ① | AstrBot 全局管理员 | WebUI 里配置的管理员，自动放行（`strict` 也放行） |
| ② | **插件配置「授权用户 ID」白名单** | ✅ **最可靠，官方机器人下请用这层**（`strict` 也放行） |
| ③ | 群内角色为群主 / 管理员 | ⚠️ 见下方限制说明；`strict` 档**不认**这层 |

### ⚠️ 关于「群主 / 群管理员」的重要限制

QQ 官方机器人的**获取群成员角色接口目前是内邀制**：

> 官方文档原文：「该能力正在内邀接入中，敬请期待」
> 错误码 `11253`：应用无接口访问权限，该接口仅白名单机器人可用，请联系平台运营申请权限

**结论**：接入**QQ 官方机器人**时，第 ③ 层（群角色判断）**通常不生效**，请依赖第 ①、② 层。
接入 **NapCat / Lagrange 等协议端**（aiocqhttp）时角色信息正常，第 ③ 层可正常工作。

### 怎么拿到自己的 ID

在群里 **@机器人发 `/whoami`**，会返回：

> ⛔ /订阅日报、/刷新赛程 等管理指令需要权限，被拦住时回复可自定义（默认：「前方的功能以后再来探索吧！趁这时间多多刷题哦！」）

```

· 用户 ID：1A2B3C4D5E6F7890...     ← 把这个填进配置
· 昵称：小明
· 群 ID：TEST_GROUP
· 群内角色：普通成员
· AstrBot 管理员：否
· 在授权白名单：否

→ 受限指令权限：❌ 无权限

📋 各指令权限（可在插件配置里改）：
✅ /日报 — 所有人
✅ /赛程 — 所有人
✅ /cf — 所有人
✅ /nk — 所有人
✅ /whoami — 所有人
❌ /订阅日报 — 授权用户
```

> 📌 **注意**：接 QQ 官方机器人时，这里的「用户 ID」是 **openid**（一长串随机字符），**不是 QQ 号**——官方 API 本身不提供真实 QQ 号。接 NapCat 等协议端时才是真实 QQ 号。

### 战绩卡片（/cf、/nk）

**默认渲染成一张图片卡片**（`profile_card_enabled`，默认开）：

- 版式模仿常见 OJ 战绩卡：头像 + 昵称 + MaxRating/段位徽章 + 大号 Rating + 本周战绩列表

- **每场比赛显示「日期 · 排名」+「过题数/总题数」**（如 `✓ 7/9`，即该场在比赛时段内
  AC 的不同题数 / 该场题目总数），**不显示 Rating 涨跌**
- 本周没比赛时，右侧显示「本周还没有打比赛，保持手感哦~」
- 头像来自平台（CF 大图优先、小图兜底 / 牛客主页并放大到 240px），
  加载失败自动回退首字母色块
  > ⚠️ CF 图床偶发头像 503：是 Cloudflare 把上游故障期的 503 缓存了 2 天
  > （响应头标记为陈旧副本），同一地址重试无用、换地址就好——插件已按

  > 强制回源（1.5.0，详见「1.5.0 更新说明」）；都失败时 15 分钟内不再重复请求，
  > 等图床恢复后自动复原。
- **图片由插件自己 `await event.send()` 发送**，发送失败（适配器不支持本地图、
  QQ 官方机器人上传富媒体失败等）会**自动改发纯文本卡片**，不会出现「没有回应」

图片发送失败或环境没有 Pillow 时，自动回退纯文本模板：

```
💡tourist
🎈Rating：3343
☁️最高Rating：4009
🔺总过题：3046
— 本周比赛战绩 —
🔸DeepInfra Round 1 (Codeforces Round 1126, Div. 1 + Div. 2)
✅7/9🚩排名：12
```

> 📌 几个细节：
> - 「本周」默认指**最近 7 天**，可在 `profile_week_days` 改
> - 缓存命中时**即时返回**；首次查询需联网（CF 约 3~6 秒，牛客约 2 秒）
> - CF 的「排名」取 **rating 更新的官方名次**（见下方说明）
> - 不想要图片、想要纯文本：把 `profile_card_enabled` 设为 `false`
> - 想在纯文本回退里显示「这周还没打比赛」，把 `profile_week_empty` 填上即可

## 战绩查询的限流与提速

查询会访问第三方接口，因此插件做了**四道闸**，避免被风控或封 IP：

| 闸 | 默认值 | 配置项 |
|---|---|---|
| 错峰并发 | 相邻请求的**发出时刻**至少间隔 1.0 秒（CF）/ 0.6 秒（牛客），**但请求本身可以重叠** | 代码内置 |
| 结果缓存 | 档案 10 分钟；单场成绩 24 小时；题库映射 24 小时（全局共用） | `profile_cache_minutes` / `profile_result_cache_hours` / `profile_problemset_ttl_hours` |
| 用户冷却 | 同一人 15 秒内只能查一次 | `profile_cooldown_seconds` |
| 全局互斥 | 同一时刻只处理一个查询，其余提示「稍后再试」 | 代码内置 |

> 💡 **「错峰并发」是什么意思？**
> 串行发请求时，三个各自要等 3 秒的请求一共要 9 秒。改成「隔 1 秒出发一个、但同时在途」之后，
> 总耗时约等于「2×间隔 + 最慢的那个」，站点收到的请求节奏一点没变密，用户却能早好几秒看到结果。

> 💡 **为什么不再拉整场榜单？**
> Codeforces 有个硬限制：非 gym 比赛的榜单**不允许多带任何参数**（带 `handles` 直接 400），
> 所以旧做法只能**整场拉回来**（实测 **5.8~8 MB / 4.5 秒**）。现在改成三条轻量路径：
>
> | 要什么 | 从哪来 | 成本 |
> |---|---|---|
> | 总过题数 | 提交记录接口 | 123 KB（本来就要拉） |
> | 该场过题数 | 同一份提交记录按时间戳切场次 | **0** |
> | 该场总题数 | 全量题库 → `{比赛: 题目数}` | 2.2 MB **一次**，所有用户共用、缓存 24 小时 |
> | 该场名次 | 比赛记录里的官方名次 | 0 |
>
> 于是单场成本从 **5.8 MB** 降到 **0**，整次查询的数据量从约 14 MB 降到约 0.13 MB。
> 只有「提交记录窗口够不着的老比赛」才会补一次单场查询（2.6 KB）。
>
> 插件启动时会在后台**预热**一次题库映射，所以第一次 `/cf` 也不用等那 2.2 MB。

> 📌 **关于 CF 的「排名」口径**：现在取比赛记录里 CF 官方 rating 更新的名次。
> 它和榜单页上看到的名次可能差几十名（榜单页默认把非正式参赛者也算进去，rating 名次只算计分的人）。
> 换来的是不用再拉 5.8 MB 榜单——两个数字都是官方的，看你要哪个口径。

## 数据文件

存放在 AstrBot 的 `data/plugin_data/astrbot_plugin_contest_daily/`：

- `contests_cache.json` — 赛程缓存（只存当前赛程，体量由数据源决定，天然有界）
- `subscriptions.json` — 群订阅表（键是会话 umo）
- `sent_log.json` — 去重表（保证提醒不重复、日报不重发；`dailyTime` 字段记「上次生效的推送时间」，1.2.17 起用来判断你是不是刚改了 `daily_time`）
- `profile_cache.json` — 战绩查询缓存（带过期时间的档案与单场成绩）
- `group_aliases.json` — 会话备注映射表 `{umo: "计科2201群"}`（1.3.0 起；面板与 `/群备注` 改它，与订阅表分开，退订不会丢）
- `quotes.json` — 名言库的自定义句子与屏蔽名单（1.6.0 起；面板「名言库」改它，与配置项 `daily_quote_extra` 合并去重）

## 缓存治理（不会无限增长）

只缓存**派生出来的小结果**，绝不把大响应留在盘上：

| 缓存 | 单条体积 | 条数上限 | 存活时间 |
|---|---|---|---|
| 用户档案 `cf:<handle>` / `nk:<uid>` | 约 0.7 KB | 各 60 条 | 10 分钟 |
| 单场成绩 `cfcs:<比赛>:<handle>` | 约 30 B | 120 条 | 24 小时 |
| 题库映射 `cfprob:counts` | 约 17 KB（全量 `{比赛: 题目数}`） | **1 条**，不参与淘汰 | 24 小时 |

- 这些都是可重建的派生数据：**超上限就丢最早写入的**，丢了再查一次就好
- 题库映射是全局共享资源（丢了要重新下载 2.2 MB），所以**不参与条数淘汰**，也不跟着 `/清缓存 cf` 一起被清（它是独立的 `题库` 类别）
- 想立刻清干净（接口抽风、数据看着不对）：`/清缓存 cf` / `/清缓存 nk` / `/清缓存 全部`，或在面板 ⑤「缓存维护」点按钮；两者都会**回复/显示具体条数**，且**不碰赛程缓存**
- 主循环每隔 `cache_cleanup_minutes` 分钟清一次：过期条目 + 超上限条目 + 已结束比赛的提醒记录
- **没有东西可清就不写盘**，避免为了「什么都没清」反复读写文件

> ⚠️ 插件**不会**把 2.2 MB 的题库原始响应存下来——写盘的只有 `{contestId: 题目数}` 这份 17 KB 的小映射。

### 磁盘图片缓存（1.2.21 起有体积兜底）

`cards/` 目录（卡片图 + `avatar_cache/` 头像）是**纯磁盘文件，不占进程内存**。
每次定期清理时依次走两道保险：

| 顺序 | 尺子 | 规则 |
|---|---|---|
| ① | 年龄 + 数量 | 超过 `card_cache_keep_days`（默认 30 天）没动过的直接删；剩下的按最旧优先删到每目录 500 个文件以内 |
| ② | **缓存总量** | 整个 `cards/` 递归统计，超过 `card_cache_max_mb`（默认 512 MB）就按最早写入的删，直到降回 80% 水位 |
| ③ | **磁盘余量** | 所在卷剩余低于 `card_cache_min_free_mb`（默认 300 MB）时，主动删图片缓存腾地方 |

第 ① 道防「慢慢变多」，第 ② 道防「文件都不老、数量也没超，但加起来太大」，
第 ③ 道防**小盘被吃满**（1.5 GB 的盘上这条往往最先触发）。三道删的都是**可重建**的缓存
（卡片图会重新渲染、头像会重新下载），且只删「最后写入超过 5 分钟」的文件。
第 ②③ 道由 `cache_cleanup_minutes`（默认 30 分钟）驱动，跑在**独立后台任务**上，
不占日报/提醒/指令的任何时间。

## 小内存部署建议（1.2.4 起实测数据）

本插件本身的内存开销**很小且不随群人数增长**，2 GB 的进程限额足够：

| 项 | 实测占用 | 说明 |
|---|---|---|
| Pillow + 卡片渲染模块 | 约 10 MB | 只在开启图片卡片时加载 |
| 渲染一张卡片 | 峰值约 3~5 MB，**反复渲染不增长** | 全局互斥锁保证同一时刻只渲染一张 |
| 字体实例缓存 | 每个 (字号,粗体) 约 0.3 MB，**已封顶 24 个**（约 7 MB） | 1.2.4 新增上限 |
| CF 提交记录解析（默认 10000 条） | 峰值约 10~20 MB，**用完立即释放** | 见下方 `profile_status_count` |
| CF 题库映射解析（2.2 MB 原始响应） | 峰值约 10 MB，解析后立刻 `del` | 只留 17 KB 的小映射进缓存 |

**1.2.4 的内存优化（实测收益）**：解析层以前写的是 `parse_x(json.dumps(data))` ——
把已经解析好的 dict 再序列化成字符串、再解析回来，等于**多造一份完整对象副本**。
实测拉一次提交记录（10000 条）要多花 **+20.9 MB 峰值 / 48 ms**，
题库映射要多花 **+9 MB / 19 ms**。现在解析函数直接吃 dict，这笔开销归零；
同时取数侧改用 `dict.pop()` 取走即释放，大 payload 不再挂到函数返回。

**2 GB 内存机器的推荐配置**（`profile_card_enabled` 视内存余量决定）：

| 配置项 | 默认 | 2 GB 建议值 | 理由 |
|---|---|---|---|
| `profile_status_count` | 10000 | **3000** | 这 10000 条提交的解析是插件最大的一笔瞬时内存；调小后峰值约降到 1/3，代价是刷题量极大的账号「总过题数」可能偏小 |
| `profile_cache_max_entries` | 200 | 100 | 纯磁盘，省 IO |
| `card_cache_keep_days` | 30 | 7 | 卡片图与头像缓存的保留天数（只占磁盘） |
| `card_cache_max_mb` | 512 | 512 | 卡片图与头像的**磁盘总量**上限（只占磁盘）；超了按最早写入删到 80% 水位 |
| `card_cache_min_free_mb` | 300 | 300 | **磁盘预留余量**：剩余低于它就主动删图片缓存腾地方（小盘必备） |
| `profile_card_enabled` | true | 内存 <1.5 GB 时可设 false | 省下 Pillow 约 10 MB 常驻 + 每次渲染几 MB 峰值 |

> 💡 群 300 人 / 日活 50 完全不影响内存：同时只允许一个战绩查询在跑
> （`_profile_lock`）+ 同一用户 15 秒冷却，峰值内存不会随并发累加；
> 查询结果本身按 200 条上限滚动淘汰，每人一条也就几 KB。

## 设计说明

**为什么赛前提醒不用固定 cron 表达式？**
因为每场比赛的开赛时刻都不同，`0 22 * * *` 这类固定表达式只能覆盖某一类比赛。
本插件用「每 30 秒扫描一次 + `sent_log` 幂等去重」实现动态倒计时提醒。

**为什么日报/提醒不直接联网？**
三条时间线解耦：只有「抓取」联网并把结果写进缓存；「日报」与「提醒」只读缓存。
这样即使抓取时网络抖动，也不会导致提醒漏发。

**为什么用 `asyncio` 自维护循环而不是 `cron_manager`？**
官方文档明确支持在 `__init__` 中 `asyncio.create_task()` 注册后台任务，行为完全可控，
且不依赖 `cron_manager` 的接口签名。所有时间参数都通过插件配置暴露，WebUI 可直接改。

**为什么「立即推送测试」按钮要做成插件可视化视图，而不是一个配置项？**
AstrBot 的插件配置表单（`_conf_schema.json`）只支持输入控件（字符串/数字/开关/列表/字典），
**没有按钮类型** —— 文档里提到的「按钮」只是 `hint` 的问号悬浮提示。所以按钮只能通过
插件可视化视图（`views/<name>/index.html` + `context.register_web_api()`）实现：
页面由 Dashboard 以受限 iframe 载入，用 `window.AstrBotPluginView` 这层 bridge 回调后端的接口
（1.3.0 起为 `status` / `push-test` / `remind-test` / `alias` / `reset-sent`）。
整套注册逻辑都包在 `try` 里，老版本 AstrBot 缺 `register_web_api` 或 `astrbot.api.web` 时
**只打一条 info 日志**，插件照常工作 —— 面板用不了还有 `/推送测试`、`/提醒测试`、`/群备注` 指令兜底。

**面板的参数是怎么读的？**
官方推荐 `from astrbot.api.web import request`，然后在 handler 里用
`request.query.get(...)` / `await request.json(default={})`。但这个 `request` 是**上下文代理**
（只在 handler 执行期间有效），离线冒烟测试里根本不存在，所以插件把它收敛成
`_params()`：运行时走官方代理，测试时注入 `self._web_req_stub`；任何读取失败都退回安全默认值，
绝不让「读参数」这件事把接口打成 500。

**为什么测试提醒**不**写幂等记录？**
`_job_remind` 靠 `sent_log.json` 的 `reminded` 表做幂等。如果测试也往这里写，
用户「测一场 → 到点真提醒被当成已提醒跳过」，当天群里一条真提醒都收不到 ——
这是最难排查的一类故障（表面看是测试通过了）。所以 `_push_remind_once()` 只发送、不记账，
日报的 `dailySent` 同样不动。

**为什么「改 `daily_time`」要靠存盘指纹而不是内存变量？**
在 AstrBot 里保存插件配置往往会**重载插件**，内存变量会被清空。如果只靠内存里的
`_last_daily_time` 判断「时间改没改过」，重载之后所有历史信息都丢了，
要么漏判（不重推）、要么每轮都误判。所以把 `(日期, 时间)` 写进 `sent_log.json` 的
`dailyTime` 字段 —— 跨重启有效，且清算后立刻写回新值，保证**恰好清算一次**。

## 已知限制

### ❗指令发出去机器人没回应？（按顺序排查）

1. **先确认跑的是最新版**：AstrBot 日志里插件拒绝/推送的日志行号会随版本变化，
   最直接的办法是看启动日志——新版会打印
   `[contest_daily] 各指令权限等级：/日报=all … /cf=all …`。
   没有这行 = 还是旧包，去插件页上传新 zip 升级。
2. **看有没有「拒绝」日志**：日志里出现
   `[contest_daily] 拒绝 cf（等级=xxx）` 说明是被插件的权限层拦的——
   检查配置「各指令权限等级」里是否给 cf/nk 设了 `admin/strict/off` 或写了
   不存在的等级值（1.2.2 起写错会回落默认，不再误拦）。
3. **只有 /cf、/nk 没回应，其他指令正常**：这两种是**发图**的指令（1.2.3 起
   发图失败会自动改发文本）。日志里找这三行——
   `查询开始` / `查询完成（x.xs）…本周 N 场` / `战绩卡片图已发送`；
   若停在「查询完成」之后没有「已发送」，看紧邻的 `战绩卡片图发送失败，回退纯文本`
   警告，把该异常发出来即可定位。
4. **日志出现 `40034102 主动消息失败, 无权限`**：这是 **QQ 官方机器人的平台限制**，
   不是插件问题——
   - 🔑 **第一件事（1.2.16）：手机 QQ → 打开那个群 → 群设置 → 机器人 → 选中本机器人 →
     打开「机器人主动在群聊内发言」**。⚠️ 这个开关是**每个群单独设置**的（不在 QQ
     开放平台里），所以「有的群能收到、有的群收不到、开放平台权限配置却一模一样」几乎都是它。
     同一位置建议把「机器人可获取的群聊消息范围」设为「获取群内全部消息」。
   - 其次再看：机器人**是否已上线**（开放平台「发布设置」提交审核后要手动点「上线」，
     未上线的沙箱期机器人主动消息通常发不出去）；上线后主动消息额度很充足
     （个人认证 60/qpm，每群每天 1000 条），日报一天 1 条远够用。
     **这不是插件能修的**；实在不行就让群友 @机器人 发 `/日报`（被动回复不受限制）。
   - ⚠️ **别把 `40034100 主动消息发送超过频控限制` 当成同一件事**：那是「发太快」，
     等额度恢复即可，与权限无关（1.2.14 起插件也不会再把它误判成永久拒绝）。
   - 🔁 **调完开关想立刻验证**（1.2.17）：AstrBot WebUI →「插件」→「竞赛日报」→「**推送测试**」→
     点「立即推送测试」，它会**无视**「今天已发过」给每个订阅群各推一条，并逐条列出哪个群成功、
     哪个群被平台拒绝。老版本 AstrBot 没有这个面板时，在群里 @机器人 发 **`/推送测试`** 一样能用。
     改 `daily_time` 也会触发「当天记录清零 + 所有群重收一遍」（见 1.2.17 说明）。
   - 官方机器人**只能被动回复**：回复 @它的消息（群聊 msg_id 有效期 5 分钟、
     每条消息最多回 **5** 次；单聊 60 分钟 / 4 次）。
     定时推送被拒时日志显示 `日报已推送 0/N 个会话，N 个被平台拒绝主动消息`；
     **1.2.13 起不会再刷屏**：平台拒绝降为 `WARNING` 且每天只提示一次（带解决办法），
     赛前提醒遇到平台拒绝立即放弃、其他故障最多重试 3 轮；启动时若检测到
     「QQ 官方机器人 + 已有订阅」也会提前提醒一次。
   - 如果连**被动回复**也报这个错，检查：机器人是否已上线/处于沙箱
     （沙箱测试群要在 QQ 开放平台「沙箱管理」里配置，未上线的 bot 在正式环境
     没有群聊发消息权限）；群管理设置里是否给机器人开了「主动回复」；
     回复是否超过了 5 分钟窗口（正常查询 3~10 秒，不会超）。
5. **卡片上头像变成「首字母方块」**（1.7.2 起这是**预期行为**，没有 QQ 头像兜底了）：
   平台头像（CF 大图 / 小图、牛客头像）**全部**没取到。常见原因：
   - CF 的大图头像**源站长期 503**（实测 8 个真实账号只 4 个能下）——
     插件会自动落到小图 `avatar`（实测 8/8 能下），所以正常情况不该是方块；
   - 该用户**从没上传过头像**（CF 会给一张全局共享的默认图，那也不是方块）；
   - 机器出网被拦 / 图床整段不可用 —— 看日志里 `平台/牛客头像全部未取到` 那行。
   - 这张卡的档案不进缓存、图片发完即删，**下次查询会重新联网**，图床恢复就自己好了。

- 牛客数据来自赛事页，**按「顶级分类」分页抓取**，
  默认只收 `13 系列赛` + `14 高校校赛`（含各校同步赛），
  **不含 `15 自主创建赛`**（数量极多，会刷屏）；想改就调 `nowcoder_categories`
- 牛客赛事页只列出**近期/精选**比赛，不含历史归档
- 抓取间隔不建议低于 10 分钟（对数据源友好）
- 本机 `curl` 访问 CF 会报 SSL 错误，本插件用 Python `urllib` 不受影响
- QQ 官方机器人下无法判断群成员角色（接口内邀制），权限请用 ID 白名单
- **QQ 头像兜底用的是「发指令的人」的头像，不是「被查的人」的**：官方机器人只给到
  应用范围内的 openid，换不出真实 QQ 号，所以拿不到被查那个 CF/牛客用户的 QQ 头像
  （1.2.9 起；查自己的战绩时正好是本人）
- **牛客只能按数字 ID 查询**（如 `/nk 886965097`），不支持昵称搜索——牛客的搜索接口需要登录态
- CF **首次查询某一场历史比赛**时会额外补一次单场查询（2.6 KB），只在「最近 10000 条提交
  覆盖不到那场比赛」时才发生；常见情况（最近一周打过的比赛）不会多花任何请求
- CF 的「总过题数」基于最近 10000 条提交统计；提交量极大的账号可能略有偏差
- CF 的「排名」取 rating 更新的官方名次，与榜单页名次可能相差几十名（口径不同，见上文说明）
